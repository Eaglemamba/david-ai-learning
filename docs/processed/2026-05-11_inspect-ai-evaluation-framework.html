快速摘要

Inspect AI 是 UK AI Security Institute（UK AISI）與 Meridian Labs 共同開發的開源 LLM 評測框架，核心價值是把「評一個模型/Agent」這件事拆成三個高度組合化的抽象 — Datasets（題目+答案）→ Solvers（解題鏈，含 Agent scaffold）→ Scorers（評分，含 LLM-as-judge）。內建 200+ 評測題庫、ReAct/Deep Agent 兩種預製 agent、MCP 工具支援、與 Docker/Kubernetes/Modal 多種 sandbox。對你正在搭建的 personal AI OS 來說，這是補上「我寫的 Skill / Agent 到底有沒有效」這個閉環的最佳工具 — 而且因為它支援 Bridge API 直接接 Claude Code 與 Gemini CLI，與你現有工具棧無縫銜接。整體技術深度高、設計哲學成熟，但門檻是需要 Python 與 async 程式基礎。

Part I — Inspect AI 是什麼？為什麼是 UK AISI 出？

Inspect AI 是一個 前沿 AI 評測框架（frontier AI evaluations framework），用 Python 寫成，在 2024 年由英國 AI Safety Institute（後來改名 AI Security Institute）開源釋出。

Inspect is a framework for frontier AI evaluations developed by the UK AI Security Institute and Meridian Labs.

它能評測的範圍包括：coding、agentic tasks、reasoning、knowledge、behavior、multi-modal understanding。不限於某個特定 task，而是設計成通用底座。

Inspect can be used for a broad range of evaluations that measure coding, agentic tasks, reasoning, knowledge, behavior, and multi-modal understanding.

為什麼是 UK AISI 出？因為英國政府在 2023 年 Bletchley Park AI Safety Summit 後成立了這個機構，任務就是「評測前沿模型」。Inspect 是他們做這件事所必須先建出來的工具基底。

💡 比喻說明

把 Inspect 想像成「LLM 界的 pytest」 — 不是給你具體的 test case（那是 200+ pre-built evals 的事），而是給你一個寫 test 的標準框架與生命週期。差別在於：傳統 pytest 是 input→assert，LLM eval 是 input→model→solver chain→scorer，多了兩層需要明確抽象。

📚 核心定位：Eval ≠ Benchmark

很多人把 eval 跟 benchmark 混為一談。Inspect 的定位是「寫一次 eval，跑遍所有模型」 — 而不是「跑 SuperGLUE 給你看分數」。

同樣是評測，benchmark 是給定題目跑分數比模型；eval 是給定模型問「這樣寫的 prompt/skill/agent 行不行」。對你的 personal AI OS 場景，後者才是你需要的。

⚠️ 為什麼挑 Inspect 而不是其他

市場上 LLM eval 框架不少（Braintrust、LangSmith、Phoenix、DeepEval、lm-evaluation-harness）。挑 Inspect 的理由：

  • 政府機構出，沒商業綁定壓力
  • Bridge API 直接接 Claude Code 與 Gemini CLI — 你已用的工具
  • 200+ 現成 eval 開箱即用
  • 支援 MCP tool，與你的擴充模型一致

Part II — 三層抽象深入：Datasets / Solvers / Scorers

層 1：Datasets — 題目與標準答案

Dataset 是一組帶 input 與 target 標記的 sample。input 通常是 prompt，target 可以是字串答案、參考輸出、或 grading rubric。

Datasets contain a set of labelled samples with input and target columns.

Inspect 支援多種來源：本地 CSV/JSON、HuggingFace datasets、自訂 loader。你也可以用程式產生 — 例如把你寫過的 100 個 prompt + 你滿意的回答 dump 成 sample.json，就是一份 dataset。

關鍵設計：Dataset 與 Solver、Scorer 完全解耦。同一份 dataset 可以餵給不同的 solver chain 跑不同實驗。

🛠️ 對照你的 library

你已有的 SkillsBench（processed/2026-03-01_skillsbench-agent-skills.html）就是「Skills 領域的 Dataset」。Inspect 的 dataset 抽象讓你可以把那個 benchmark 直接 wrap 起來，跑你自己的 Skill 看分數。

層 2：Solvers — 解題鏈，含 Agent scaffold

Solver 是處理 input 並產出結果的元件，可以串成 chain。最基本的 solver 是 generate()（直接呼叫模型），但你可以前後加上：

  • chain_of_thought() — 加 CoT 提示前綴
  • self_critique() — 讓模型自我檢查
  • use_tools() — 開啟 tool calling
  • react() — 跑 ReAct agent loop

Solver 也可以是完整 Agent scaffold — Inspect 內建 ReAct 與 Deep Agent，並支援用 Bridge API 接外部 agent（Claude Code、Gemini CLI、自家 Hermes 都行）。

📚 為什麼解題鏈值得抽象

「同一題用不同 prompt 技巧解」是 LLM 工程的核心實驗。Solver 把 prompt 技巧變成可組合的中介軟體（middleware），讓你能 A/B 測試不同 chain 對同一 dataset 的影響，而不用每次重寫整套程式。

# 一個典型的 Solver chain — theory of mind eval
solver = chain(
    chain_of_thought(),       # 提示模型逐步推理
    generate(),               # 呼叫模型
    self_critique(),          # 讓模型回頭自查
)

scorer = model_graded_fact()  # 用另一個模型評分（LLM-as-judge）

層 3：Scorers — 評分，含 LLM-as-judge

Scorer 接收 solver 的最終輸出，產出一個 score。內建幾種：

  • match() — 完全字串比對
  • includes() — 包含關鍵字
  • pattern() — regex 比對
  • model_graded_fact() — 用另一個模型當裁判
  • model_graded_qa() — QA 任務專用 LLM-judge
  • 自訂 @scorer — 你可以寫任意邏輯

關鍵設計：同一個 sample 可以跑多個 scorer — 你可以同時要 exact match + 用 LLM 判斷語意相近，然後比較。

⚠️ LLM-as-judge 的陷阱

用模型評分聽起來很方便，但有兩個經典坑：

  • position bias：裁判模型偏好先出現的選項
  • length bias：裁判模型偏好較長的回答

Inspect 的 model_graded_* 系列已經內建了一些 mitigation（如位置 randomize），但你還是該對 judge prompt 自己做 calibration。

Part III — Agent 評測：為什麼這是 Inspect 的殺手鐧

傳統 LLM eval 把模型當成「文字 in / 文字 out」的黑盒。Agent 不是。 Agent 會呼叫工具、執行程式碼、查網頁、跑很多輪，且每一步都可能出錯。

Inspect 的 agent eval 設計面向這個現實：

  • 內建 agent：ReAct、Deep Agent 開箱即用
  • Multi-agent primitives：可以跑多 agent 協作場景
  • Bridge API：接 Claude Code、Gemini CLI、任意 external agent
  • Sandbox：Docker / Kubernetes / Modal / Proxmox 隔離執行環境
  • Tool support：bash、python、text editor、web search、web browser、computer use 都是內建 tool
  • MCP tool 整合：你寫的 MCP server 可以直接當 eval tool
🛠️ 對你 Hermes / Skill-creator 軌跡的延伸

你最近收的 Hermes Agent（self-improving）、Skill-creator epic update（含「評估系統」）、SkillsBench 三篇都在處理「Agent 該怎麼自我驗證」。Inspect 是把這個能力從特定 agent 抽出來變成獨立工具層的代表 — 任何 agent 都可以 plug 進來被評。

具體：你的 Hermes 是 self-evaluator（自評），Inspect 是 third-party evaluator（他評）。兩者組合才是完整 feedback loop。

⚠️ Sandbox 的真實價值

Agent 跑 bash / python 是高風險動作。Inspect 的 sandbox 不是裝飾 — 它是真的把每個 agent 執行隔離在 container 裡，evals 跑完容器銷毀。

你跑自家 Hermes 跑 100 次 self-improvement 不會搞爛你的本機。

Part IV — 從零開始：第一個 eval 怎麼寫

💻 安裝與基本指令

標準 Python pip 安裝，設好 API key 後一行指令就能跑：

# 安裝
pip install inspect-ai

# 設定 API key（任一供應商皆可）
export ANTHROPIC_API_KEY=sk-ant-...
export OPENAI_API_KEY=sk-...

# 跑一個現成的 eval（例如 ARC reasoning benchmark）
inspect eval arc.py --model anthropic/claude-opus-4-7

# 用 Inspect View 視覺化結果
inspect view
🛠️ 寫你自己的 eval — 三步

Step 1：準備 dataset。把你寫過的 20 個你最常用的 prompt + 你期望的輸出 dump 成 JSON。

Step 2：定義 task。用 @task decorator，宣告 dataset、solver chain（從最簡單的 generate() 起）、scorer（先用 model_graded_fact()）。

Step 3：跑。inspect eval my_skill.py --model anthropic/claude-opus-4-7。看 Inspect View，找出哪些 sample fail，回頭調 Skill。

重點整理 Key Takeaways

1. 三層抽象是 LLM eval 的「對的切法」
Datasets / Solvers / Scorers 解耦讓你能「同題不同 prompt」「同 prompt 不同 model」「同模型不同 scorer」三軸獨立實驗。這是傳統 metric-based eval 做不到的彈性。
2. Agent eval 是 2026 的剛需
當你的工作對象從 prompt 變成 agent（你已經到這了），eval 工具也必須升級。Inspect 是少數把 agent + sandbox + tool 都當一等公民的框架。
3. 政府機構出 = 沒有商業包袱
Braintrust / LangSmith 都是 SaaS，要你 push trace 上他們服務器。Inspect 完全本地，你的 prompt / 輸出不外流。對 personal AI OS 場景這是關鍵。
4. 入門門檻：Python + async + 寫 dataset
Inspect 不是「點點按鈕」工具。需要會 Python、能讀 async、願意自己準備 dataset。投入後的回報是「你寫的每個 Skill 從此都能客觀比較」。

練習題 Practice Questions

先在心中思考答案，再點開展開查看建議答案。

Q1 概念理解 為什麼 Inspect 要把 eval 切成 Datasets / Solvers / Scorers 三層？合在一起寫不行嗎？

合在一起寫的問題：你會發現你寫了 50 個 eval 之後，每個都是「題目+模型呼叫+評分邏輯」綁死，要換 prompt 技巧得改 50 個檔案，要換 scorer 也得改 50 個檔案。這就是耦合的成本。

三層抽象的真正價值：三軸獨立實驗。同一份 dataset 可以跑「generate() only」vs「chain_of_thought() + generate() + self_critique()」兩種 solver，比較哪個 chain 對這類題目更有效；同一個 solver 可以跑「match()」vs「model_graded_fact()」兩種 scorer，看 LLM-judge 與 exact match 的相關性。

這個切法直接對應「LLM 工程的三大不確定性」 — 題目選對了嗎、prompt 寫對了嗎、評分標準合理嗎。三層分開才能各別 debug。

Q2 應用設計 你想為現有的某個 Skill 寫第一個 Inspect eval，最小可行版本應該包含什麼？

最小可行 eval 包含三件事：

  • Dataset：10–20 個你過去實際用這個 Skill 處理的「input + 你滿意的輸出」配對。先用 JSON 存。不需要完美，只要代表你常用的場景即可。
  • Solver：從最簡單的 generate() 起步，把你的 Skill 內容當 system prompt 注入。後續才加 chain_of_thought() 等技巧做 A/B。
  • Scorer：先用 model_graded_fact()，judge prompt 寫成「比較模型輸出是否捕捉到了 target 中的核心要點」。日後再做 calibration。

關鍵心態：第一版 eval 不會完美。重點是建立 baseline，之後改 Skill 時能客觀看出「分數有沒有變好」 — 這個 baseline 比追求一次到位重要 100 倍。

Q3 批判思考 Inspect 內建 200+ evals，但你真的需要它們嗎？什麼情況該用內建 eval、什麼情況該自己寫？

內建 eval 的價值：當你想知道「我的模型 setup 在通用基準上表現如何」 — 例如 ARC、GSM8K、HumanEval — 這些是學界共識的能力檢測，跑一輪就有業界比較基準。

內建 eval 的盲點：它們無法告訴你「我寫的 Skill 對我的工作場景好不好用」。MMLU 跑 90 分不代表你的 /triage-deviation skill 寫得好；HumanEval 高分也不代表你的 cdmo-feasibility skill 對你客戶的真實案例有用。

實務分工：

  • 內建 eval：新模型出來、想換 base model、想知道你的 prompt 技巧在通用題上有效嗎 — 用內建。
  • 自寫 eval：每個 production Skill 都該配一份自寫 eval，反映你的真實使用場景。內建 eval 永遠取代不了這個。

類比：內建 eval 是「健身房體測」，自寫 eval 是「你能不能扛起家裡的水桶」。前者標準化，後者實用。兩者都需要，但別搞反了。

🎯 我的行動結論
✔ 核心洞察
Inspect AI 用三層抽象（Datasets / Solvers / Scorers）把 LLM eval 從「臨時腳本」升級為「可組合的工程框架」 — 這正是我目前 personal AI OS 缺的拼圖。我寫了一堆 Skill 與半套 Agent，但完全沒有 systematic feedback loop 告訴我哪個有效、哪個改壞了。Inspect 是補上這塊的最佳起點。
📈 立即應用
本週可做：（1）pip install inspect-ai + 跑一個內建 eval（例如 ARC）熟悉 CLI 與 Inspect View；（2）為其中一個我最常用的 Skill 整理 10–15 組 input/target，寫成 dataset.json；（3）寫一個最小 task，用 generate() + model_graded_fact() 跑出第一個 baseline。整套大約 2–3 小時可完成。
⚠ 需要補充
這份是工具入門，不是設計方法論。後續還需要補：（1）eval design 本身的方法 — Anthropic 的「Building Effective Evals」guide、Hamel Husain 的 eval blog 系列；（2）LLM-as-judge 的 calibration — judge prompt 怎麼寫才不偏；（3）Braintrust 對照閱讀，看商業產品在 trace + dashboard 上多做了什麼，決定要不要混搭。三個月後重讀本文時，重點應該放在「我跑了多少 eval、改了多少 Skill」而非框架本身。
