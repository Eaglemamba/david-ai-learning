Part 1資訊密度 Information Density
Markdown 已經成為 Agent 與我們溝通的主流檔案格式。它簡單、可攜、有基本的富文本能力，而且容易讓你親自編輯。Claude 甚至意外地擅長用 ASCII 在 Markdown 裡畫圖。
"Markdown has become the dominant file format used by agents to communicate with us. It's simple, portable, has some rich text capability and is easy for you to edit."
但隨著 Agent 變得越來越強大，我感覺 Markdown 變成一種限制性的格式。我發現很難閱讀超過一百行的 Markdown 檔案。我想要更豐富的視覺呈現、顏色和圖表，並且能夠輕鬆分享。
"As agents have become more and more powerful, I have felt that markdown has become a restricting format. I find it difficult to read a markdown file of more than a hundred lines."
HTML 可以承載比 Markdown 豐富得多的資訊：表格資料、CSS 設計、SVG 插圖、JavaScript 程式碼、HTML+JS+CSS 的互動、SVG+HTML 的工作流程、絕對定位的空間資料、圖片標籤等等。
"HTML can convey much richer information compared to markdown... tables, CSS, SVG, script tags, interactions, workflows, spatial data, images."
我會說，幾乎沒有 Claude 能讀的資訊集合，是無法用 HTML 高效表達的。這讓 HTML 成為模型向你傳達深度資訊、以及讓你檢視資訊的高效方式。
"There is almost no set of information that Claude can read that you cannot fairly efficiently represent with HTML."
💡 比喻：紙本 SOP vs. eBR (電子批次紀錄)

Markdown 像是紙本 SOP：簡單、可攜、容易拿筆修改。但當資訊量大到一定程度（像是 100 頁的 Master Batch Record），紙本就難以快速查找重點。

HTML 則像是eBR (Electronic Batch Record)：可以巢狀檢視、搜尋、附加圖表、即時驗證資料。當你的 Agent 在處理複雜任務時，你需要的是 eBR 而不是紙本。

⚠️ 反直覺洞察

當 Claude 必須在 Markdown 表達顏色時，它會用Unicode 字元（彩色方塊）來估算 RGB 值。這是格式限制下的扭曲行為。

就像強迫操作員用紙本記錄連續監控資料：他們會自己畫表格、創造非正式符號。問題不是操作員，是工具。

📚 核心概念：表達能力決定產出品質

當輸出格式無法承載概念，模型必須做妥協（壓縮資訊、用 ASCII 圖、放棄細節）。

HTML 移除了這個瓶頸 → 模型不再需要妥協 → 你看到的是它真正能表達的，而不是它能塞進 Markdown 的。

Part 2視覺清晰度 & 易於分享 Visual Clarity & Sharing
當 Claude 能做更複雜的工作時，它也在寫更大的規格和計畫。實務上，我發現自己不太會閱讀超過 100 行的 Markdown 檔案，更不用說讓組織裡其他人讀。
"As Claude is able to do more complex work, it is also writing larger and larger specs and plans. In practice, I've found I tend to not actually read more than a 100-line markdown file."
但 HTML 文件容易閱讀許多。Claude 可以視覺化地組織結構，搭配分頁、插圖、連結等。它甚至可以做行動裝置響應式，讓你根據裝置不同方式閱讀。
"HTML documents are much easier to read, Claude can organize the structure visually to be ideal to navigate with tabs, illustrations, links, etc. It can even be mobile responsive."
Markdown 檔案很難分享，因為大多數瀏覽器不會原生渲染。你常常必須以附件方式加到 email 或訊息中。
"Markdown files are fairly hard to share since most browsers do not render them natively well."
用 HTML，只要你把檔案上傳（例如到 S3），就可以輕鬆分享連結。你的同事可以在任何地方打開、輕鬆參考。「你的規格、報告或 PR 紀錄被人實際閱讀的機率，會大大提升」。
"The chance of someone actually reading your spec, report or PR writeup is much much higher if it's in HTML."
🛠️ 實務應用：你的 Dashboard 已經在做這件事

你的 65+ HTML 學習文件 + GitHub Pages，正是 Thariq 描述的模式：檔案產出後可以立即用連結分享，不需要先下載再附件。

下一步可以延伸到：把Tech Transfer 規格、Deviation Investigation 報告也輸出為 HTML，給內部 QA 和客戶閱讀。比 PDF 更具表達力，比 Word 更易於分享。

💡 比喻：A4 紙 vs. 大型海報

Markdown 像 A4 紙：每頁有限，超過 100 行就讓人想「跳過」。

HTML 像研討會用的大型海報：可以分區、用顏色標示、放圖表。讀者用「掃描」而不是「逐行閱讀」就能抓到重點。對於忙碌的主管來說，這個差異決定了訊息能否傳達。

⚠️ 重點提示：分享機率 = 訊息價值 × 易讀性

一份精彩的規格如果沒人讀，價值等於零。這對於想要影響組織決策的人來說特別重要。

對於你 COO 軌道的目標來說，把 Strategy Memo、季度檢討、跨部門提案改用 HTML 輸出，可以顯著提升組織內被閱讀和被引用的機率。

Part 3雙向互動 & 資料注入 Two-way Interaction & Data Ingestion
HTML 可以讓你與文件互動。例如你可以要 Claude 加上滑桿或旋鈕來調整設計，或讓你調整演算法的不同選項看會發生什麼事。
"HTML can allow you to interact with the document, for example sliders or knobs to adjust a design or tweak different options in the algorithm."
你也可以要它讓你把這些變更複製成一段 prompt 貼回 Claude Code。這就是「Copy as JSON」或「Copy as Prompt」按鈕的設計模式：把 UI 操作的結果轉換回模型可以消化的格式。
"You can also ask it to let you copy these changes into a prompt to paste back into Claude Code."
為什麼用 Claude Code 來產 HTML，而不是用 Claude.ai 或 Claude Design？最大的原因之一是 Claude Code 能注入的上下文：你的整個程式碼資料夾、MCP 連線（Slack、Linear 等）、Chrome 瀏覽器內容、git 歷史等等。
"One of the biggest reasons is all the context Claude Code can ingest... file system, MCPs, web browser, git history."
舉例來說，當寫這篇文章時，Thariq 要求 Claude Code 讀過他的程式碼資料夾、找出所有 HTML 檔案、分組分類，然後做出一個 HTML 檔案展示每種類型的圖表。這篇文章的所有圖表都是這樣產生的。
"When writing this article, I asked Claude Code to read through my code folder and find all the HTML files I've generated, group and categorize them and then make an HTML file with all diagrams."
💻 互動模式三範例

1. 拋棄式編輯介面：30 張 Linear ticket 拖拉到 Now / Next / Later / Cut 四欄，按鈕匯出 markdown。

2. Feature Flag 編輯器：依區域分組、顯示依賴關係、警告前置條件未開啟，匯出 diff。

3. Prompt 調校工具：左側可編輯 prompt 含變數 slot、右側即時渲染三組樣本輸入。

🛠️ CDMO 實務映射

製程參數調校工具：滑桿調整溫度/時間/速度，即時計算填充均勻度預測，按鈕匯出為 batch protocol 變更請求。

Deviation Triage 介面：拖拉異常事件到「立即上報 / 需調查 / 趨勢監控 / 結案」四欄，匯出為 CAPA 草稿。

Tech Transfer Risk Map：互動式風險矩陣，調整客戶/產品/設備變數，即時更新 risk score。

⚠️ 重點：Context Engineering 的優勢

Claude.ai 的 Artifact 雖然也能做 HTML，但無法存取你的整個 GitHub Repo、Slack、git 歷史。Claude Code 才能做到「讀完整套程式碼後產出 HTML」這種深度整合。

這也呼應你正在實踐的「上下文勝於指令」原則。

Part 4五大使用場景 Five Use Cases
① 規格、規劃與探索 Specs, Planning & Exploration
"HTML is a rich canvas for Claude to dive into a problem."
當開始處理問題時，不要用單一 Markdown 計畫，期待產出一張 HTML 檔案的網絡。先讓 Claude 腦力激盪 6 種不同方向、做成 grid 並排比較；選定方向後請它擴展、做 mockup、加入程式碼片段；最後寫實作計畫，新開 session 把所有檔案傳入實作。
"Generate 6 distinctly different approaches and lay them out as a single HTML file in a grid so I can compare them side by side."
② 程式碼審查與理解 Code Review & Understanding
"Code can be difficult to read in a Markdown file."
用 HTML 可以渲染 diff、註解、流程圖、模組關係。Thariq 表示他現在每個 PR 都附上一個 HTML 解說。比 GitHub 預設的 diff view 更易理解。
"I find this often works better than the default Github diff view, and I attach a HTML code explainer to every PR I make now."
③ 設計與原型 Design & Prototypes
"HTML is incredibly expressive at design."
即使你的最終介面不是 HTML（例如 React、Swift），Claude 也可以先用 HTML 草擬設計再轉換。也可以原型化動畫、滑桿，要 Claude 給「複製參數」按鈕，把對得起來的設定貼回。
"Claude can sketch out a design in HTML and then write it in your language of choice."
🛠️ ④ 報告、研究與學習

Claude Code 擅長跨多個資料來源（Slack、git history、網路）合成資訊並轉為易讀報告。可以產出：

  • 長篇 HTML 文件
  • 互動式解說頁
  • 投影片/簡報
  • SVG 流程圖、技術圖解

映射你的情境：週報給主管、Incident Report 給高層、Feature 解說、年度 Earnings Decipher、CB Daily Digest——都適用此模式。

⚖️ ⑤ 客製化編輯介面（最有趣的場景）

當很難用純文字描述你想要的東西時，請 Claude 為這件事打造一個拋棄式編輯器。不是產品、不是可重用工具，就是一個 HTML 檔案，為這一份資料量身打造。

關鍵是結尾要有匯出按鈕：「Copy as JSON」或「Copy as Prompt」，把 UI 操作的結果轉回可貼回 Claude Code 的東西。

⚠️ 適用場景清單

用拋棄式 HTML 編輯介面處理：

  • 重新排序、分類任何東西（tickets、test cases、回饋）
  • 編輯有約束的結構化設定（feature flag、env vars、JSON/YAML）
  • 調校 prompt、模板、文案，含即時預覽
  • 策展資料集，標記、選擇、匯出
  • 選擇難以用文字表達的值：顏色、easing 曲線、裁切區域、cron schedule、regex
Part 5權衡取捨 Trade-offs & Critical Evaluation
Q1: HTML 不是比較不省 Token 嗎？
"Isn't it less token efficient?"
Markdown 通常 Token 用量較少，但 Thariq 認為 HTML 的表達力 + 你實際會閱讀的高機率，整體產出更好。Opus 4.7 有 1MM context window，所以 Token 增加在實務上不太明顯。
"With the 1MM context window in Opus 4.7, the increased token usage is not really noticeable."
Q2: 生成 HTML 不是比 Markdown 慢嗎？
"Doesn't this take longer to generate than markdown?"
確實會慢 2-4 倍。但 Thariq 認為值得：你會真的讀。
"HTML can take 2-4x longer than Markdown, but I've found the results are worth it."
Q3: 版本控制怎麼辦？
"What about version control?"
這是 HTML 最大缺點之一。HTML 的 diff 很雜亂，很難 review，與 Markdown 比起來。
"HTML diffs are noisy and hard to review compared to Markdown."
Q4: 怎麼讓 HTML 不醜？
"How do I get Claude to match my taste / not make it ugly?"
用 frontend design plugin。要符合公司風格，可以指向你的 codebase 建立一份 design system HTML 當參考。
"Create a single design system HTML file by pointing Claude at your codebase."
⚠️ 來源偏誤評估（2-3x Discount Principle）

Thariq 在 Anthropic Claude Code 團隊內部任職。他的核心利益是讓 Claude Code 的能力被看見並被使用。

他自承「我可能在 HTML maximalist 那一邊」（I'm probably far on the HTML maximalist side of things）——這是文章中少數的誠實校準。

讀者應打折的部分：HTML 取代 Markdown 的範圍。對組織內部分享、研究報告、原型設計，HTML 確實有優勢；但對每日 chat 對話、簡短備忘、需要 git diff review 的文件，Markdown 仍佔優。

⚖️ Markdown 仍勝出的場景

儘管 Thariq 說「我已經幾乎完全停用 Markdown」，下列場景仍應用 Markdown：

  • 需要 git diff 審查的文件（README、ARCHITECTURE、ADR）
  • 純文字檢索/grep 的場景（你會用 ripgrep 搜尋的內容）
  • 機器消費的文件（LLM 讀取的 index.md、SKILL.md）
  • 極短的備忘（< 50 行，沒有圖表需求）
⚠️ Token Cost 的真實計算

1MM context window 不代表「Token 不重要」。對 Max 5x 用戶來說：

HTML ≈ Markdown × 2.5-4x 在輸出端，意味著訊息額度消耗速度也會增加 2-4 倍。對於每月用量緊張的使用者，這是真實成本。

建議：高價值任務（報告、規格、學習文件）用 HTML；快速腦力激盪、私人筆記用 Markdown。

重點整理 Key Takeaways

1. 表達能力 > 編輯便利

當你不再親手編輯文件，而是讓 Claude 修改文件時，Markdown「易於手動編輯」的優勢就消失了。這時應選擇對讀者最友善的格式。

2. HTML 四大支柱

資訊密度（表格、SVG、CSS）、視覺清晰（>100 行也易讀）、易於分享（瀏覽器原生）、雙向互動（滑桿、按鈕、Copy as Prompt）。

3. 拋棄式編輯介面

最具創意的應用：請 Claude 為單一資料量身打造一次性 HTML 編輯器，結尾必須有「Copy as JSON / Prompt」按鈕，把 UI 操作結果轉回模型。

4. 不要過度美化為 Skill

Thariq 警告：不要把這變成 /html skill。直接 prompt「make a HTML file」，根據情境調整。經驗累積後再思考是否抽象化。

練習題 Practice (Active Recall)

Q1 概念理解 為什麼 Thariq 認為 Markdown「易於手動編輯」這個優勢正在失效？

因為當 Agent 變得越來越強大，使用者不再親自編輯文件，而是 prompt Claude 去修改。

Markdown 的設計初衷之一是「人類能輕鬆用任何文字編輯器修改」。但如果你都用 Claude 修改，這個優勢就消失了——這時應該選擇對讀者最友善而不是對「手動編輯者」最友善的格式。

這個論點本質上揭露了一個更深的轉變：當 AI 接管「編輯」這個動作後，人類唯一保留的角色是「讀者」。優化目標應該重新校準到讀者體驗。

Q2 產業應用 在你的 CDMO 情境中，最適合從 Markdown 切換到 HTML 的三種文件類型是什麼？為什麼？

① Tech Transfer 規格文件給客戶：客戶不在公司內部，無法存取你的 GitHub。HTML 可以直接以連結分享，含製程流程圖（SVG）、設備配置（CSS layout）、互動式參數比較表。

② Deviation Investigation 報告給高層：高層只會掃描重點。HTML 可以分頁呈現「事件描述 / 根因分析 / CAPA / 趨勢」，附風險矩陣 SVG，讓 30 秒掃描就能抓到重點。

③ 季度 Operations Review 給 COO/CEO：HTML 可以做互動式 dashboard，含 batch yield 趨勢、設備稼動率、客戶滿意度。比 PowerPoint 更易分享，比 PDF 更具表達力。

但仍應留在 Markdown 的：SOP（需要 git diff 審查、QA 簽核流程、機器可讀）、Internal Knowledge Base 的 index 檔（給 LLM grep）、SKILL.md 檔。

Q3 批判思考 Thariq 在文章中說「我已經幾乎完全停用 Markdown」。這個立場有什麼盲點？對你的知識管理體系有什麼啟示？

盲點一：Markdown 在 LLM 消費端仍是首選。Karpathy 的雙輸出架構（.md 給 LLM 查詢，.html 給人類瀏覽）正反映這點。Thariq 是 Anthropic 工程師，他的 Claude Code 可以直接讀 HTML，但其他工具鏈（grep、ripgrep、Obsidian、其他 LLM）對 Markdown 友善得多。

盲點二：Token 經濟學被輕描淡寫。「1MM context window 所以 Token 不重要」是 Anthropic 員工視角。對 Max 5x 用戶，每月訊息額度真實存在。HTML 慢 2-4 倍 + Token 多 2-4 倍 = 訊息額度消耗加倍。

盲點三：版本控制成本。Thariq 自承「HTML diff 雜亂」，但沒展開討論。對於需要長期維護的文件（一年後還會修改的），Markdown 的可審查性是關鍵價值。

啟示：你的雙輸出架構（.md + .html）才是正確答案。不要被 Thariq 的單一立場帶偏。Markdown 給機器、給歷史審查、給 grep；HTML 給當下的人類讀者、給互動、給分享。選擇格式應該基於「誰是消費者」，不是哲學立場。

🎯 我的行動結論 Bottom Line for Me
✔ 核心洞察
當 AI 接管「編輯」動作後，人類角色變成純讀者。文件格式應優化為「讀者友善」而非「編輯者友善」。我的 HTML Learning Library 走在這個方向，但 Thariq 揭示的更大版圖是——這個原則應該擴展到 Tech Transfer 文件、Deviation 報告、季度 Operations Review 等所有給「他人閱讀」的文件。
📈 立即應用（本週）
下一份要寫的 Tech Transfer Risk Assessment，直接用 HTML 輸出。包含：互動式風險矩陣（客戶/產品/設備變數可調）、製程流程 SVG、CAPA 草稿區、Copy as Email 按鈕。觀察客戶閱讀行為與回饋速度，與過去 PDF/Word 對比。如果驗證為真，把它升級為 /tech-transfer-html skill。
⚠ 需要補充
文章避談的問題：（1）HTML 在 GMP 環境的稽核留痕困難——FDA/PIC/S 稽核員偏好 PDF/紙本。（2）HTML 文件的長期保存挑戰——CSS/JS 隨瀏覽器演進可能失效，10 年後還能正確渲染嗎？（3）需要建立HTML→PDF 轉換 SOP，確保正式記錄仍有可審計版本。3 個月後重讀，檢視 GMP 法規對 HTML 文件的接受度發展。
