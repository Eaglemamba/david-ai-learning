Part I — 什麼是 Markdown 檔案？

Markdown 檔案就是一個 輕量純文字檔（Lightweight Plain-Text File），副檔名是 .md，僅此而已。

A Markdown file is just a lightweight plain-text file with a .MD extension. That is it.

你只需要使用像是 #、-、* 這幾個簡單符號，就能產生對應的格式輸出。

You use characters like "#", "-", and "*" to produce specific outputs.

Markdown 的核心特性是：可攜（Portable）、本地離線儲存、極簡易用。

Markdown files are portable, stored locally and offline, and just generally easy to use.

💡 比喻說明

把 Markdown 想成是「桌面版的 Google Docs」— 一種極簡的文字建立與編輯方式。Obsidian 這類筆記軟體之所以受歡迎，就是因為它原生使用 .md 格式，極簡又不被任何單一供應商綁住。

📚 核心概念：純文字優勢

.md 檔案本質上和你寫在記事本裡的文字一樣 — 沒有隱藏的字型定義、樣式標籤、版本控制元資料。這個「沒有」正是它對 AI 最大的價值。

對 CDMO 場景的對照：就像 GMP 文件中的 純文字 SOP 流程描述，相較於充滿表格、圖片、Excel 連結的混合式文件，純文字 SOP 更容易被自動化工具讀取、版本控制、搜尋比對。

💻 Markdown 基本語法

標題、清單、強調文字 — 三組符號就能涵蓋 80% 的格式需求。

# 這是一級標題

## 這是二級標題

這是一段普通段落文字。

- 這是一個項目符號
- 這是另一個項目符號

**這段文字會變成粗體**

Part II — 為什麼 Markdown 對 AI 特別有效？

當你傳訊息給 AI 時，它把所有內容當作 資料流（Stream of Data）來處理 — 它看不到人眼看到的格式美感。

When you send a message to any AI, it processes everything as a stream of data (it does not see formatting the way a human eye does).

AI 不會欣賞精美設計的 Word 文件或乾淨的 PDF 排版。它看到的是底層文字，而所有非文字的東西都是它必須先過濾或解碼掉的雜訊（Noise）。

It does not appreciate a beautifully designed Word document or a clean PDF layout. What it sees is the underlying text, and anything that is not text is noise it has to filter out or decode before getting to the actual content.

這就是為什麼大多數檔案格式在搭配 AI 時會失敗的根本原因。

This is why most file formats fail when used with AI.

一個 Word/Google Doc 檔案內含數百個隱藏標籤、字型定義、邊距設定、元資料，這些都和你寫的內容無關。

A Google/Word document contains hundreds of hidden tags, font definitions, margin settings, etc., etc. Not to mention all the metadata that has nothing to do with what you wrote.

AI 必須先過濾這些資料才能產生輸出，這會浪費你的時間和 Token（也就是錢）。

AI has to filter ALL that data before it can produce an output, costing you time and tokens (money).

📚 核心概念：Token 經濟學

每次 AI 處理文件，都要把 解析格式 的成本算進 Token。Word/PDF 內含的 XML 標籤、樣式定義、二進位資料雖然「對 AI 不可見」，但仍然會佔用解析資源。

Markdown 的優勢：輸入幾乎等於輸出語意，沒有額外的解析開銷。

⚠️ 批判視角：原文略簡化

實務上，現代 AI（如 Claude、GPT-4o）處理 PDF 與 Word 已相當成熟，並非「失敗」。原文的「fail」是行銷修辭，更精準的說法是：Markdown 的訊號雜訊比（Signal-to-Noise Ratio）最高，因此在大量、長期、重複使用的情境下成本效益最佳。

套用 2-3x 折扣原則：把「AI 完全看不懂 PDF」當作 「Markdown 在批次自動化情境下更便宜」 來理解就對了。

🛠️ CDMO 場景對照

這個原則和 21 CFR Part 11 對電子紀錄的「結構化資料」要求 邏輯一致 — 純文字、可審計、無隱藏元資料的格式，永遠比格式化的 Word 文件更適合長期儲存與自動化處理。

Part III — 如何建立 .md 檔案？三種方法

作者建議先在桌面建立一個資料夾，命名為 「AI Markdown Vault」，作為所有 .md 檔案的中央倉庫。然後從以下三種建立方式選一個或組合使用。

📚 方法 1：作業系統內建文字編輯器

Mac 使用者：用 TextEdit。Windows 使用者：用 Notepad。

新增文件，存檔時把副檔名改為 .md，存到你的 AI Markdown Vault 資料夾即可。零成本、零學習曲線。

🛠️ 方法 2：Claude Cowork（推薦）

由於 Claude Cowork 可以直接掛載本地桌面資料夾，你可以開一個新對話，把整個 AI Markdown Vault 資料夾附上，然後讓 Claude 代你建立、整理、更新檔案。

實務優勢：對話式建檔 — 你描述需求，Claude 直接寫好 .md 並存到對的位置。對 David 而言，這和你已經在用的 Claude Code 桌面工作流邏輯接近。

⚖️ 方法 3：第三方筆記 App（Obsidian）

原文作者推薦 Obsidian — 它原生使用 .md 格式，支援 Wikilinks、雙向連結、圖譜檢視，特別適合建立「知識網絡」而非「平面檔案」。

對你的延伸：這正是你已經在規劃的「Skill graph」探索方向。Obsidian 的 Wikilinks + YAML frontmatter 模式，是把扁平 SKILL.md 演化為互聯知識圖譜的成熟參考。

Part IV — Markdown 的三大使用情境

這是整篇文章最有價值的部分。AI Edge 提出三層架構：Memory（記憶）、Skills（技能）、Project Instructions（專案指令）。三者各司其職，組合起來就是一個完整的個人 AI 知識管理系統。

情境 1：記憶與脈絡檔案（Memory and Context Files）

這是 Markdown 最有價值的實務應用之一。你可以用 AI Markdown Vault 資料夾儲存所有 AI 資料，建立一個 自我進化的記憶系統（Self-evolving Memory System）。

This is one of the most useful practical applications of Markdown. You can use your new AI Markdown Vault folder to store all your AI data and create a self-evolving memory system.

這樣儲存的好處是：你可以在任何 AI 工具之間無縫切換，並隨需載入你所有的脈絡與偏好。

By storing your data this way, you can seamlessly switch between any AI tool and have it load all your context, preferences, etc. on demand.

簡言之：把你的 AI 指令、工作流、提示詞建立成 Markdown 檔案，存放在 Vault 中，就獲得一個 無上限、本地儲存、離線可用的 AI 記憶。

TLDR: Create Markdown files that store your AI instructions, workflows, prompts, etc. in your AI Markdown Vault. This gives you unlimited, locally stored, offline AI memory that can be organized and used in any AI tool.

💡 比喻說明：可攜式員工手冊

想像你帶一本「個人員工手冊」去任何新公司報到 — 上面記錄了你的工作風格、專案脈絡、偏好的溝通方式。新公司不需要重新訓練你，只要看手冊就能立刻協作。

Memory.md 就是給 AI 看的這本手冊。換 AI 平台不用重新教 — 換工具，不換脈絡。

⚠️ 重點提示：你已經有更成熟的版本

你目前的 Claude.ai 內建記憶系統 + 自動化 Pipeline（Gmail → Make.com → GitHub → Claude Code → HTML）已經比這個手動 .md 系統更進階。

但這篇文章值得參考的是 — 把所有指令文字化、版本化、可攜化的設計哲學，正是你已經在實踐的 dual-output（.md + .html）系統的同源思想。

情境 2：AI 技能（AI Skills）

AI Skill 是一個 SOP，把 LLM 變成特定工作流的專家（例如 Claude Skills）。

An AI Skill is an SOP that turns LLMs into a specialist for a specific workflow (like Claude Skills).

作者建議：把你所有的 AI Skills 全部轉換成 Markdown 檔案。這樣做的好處：

What I recommend doing is taking your AI Skills and converting them all into Markdown files.

  • 可以在任何 AI 跨平台使用
  • 可以從中組合出 mega prompts（巨型提示詞）
  • 不被單一平台綁死
🛠️ 你的 Skills 架構對照

你已經實踐了這個建議：artifact-skill、cdmo-feasibility-assessment、amaran-presentation、開發中的 /triage-deviation — 全部都是 SKILL.md 格式。

原文的關鍵洞察值得記住：SKILL.md 不只是 Claude Code 的內部格式，而是一種跨平台可攜資產。同一個 SKILL.md 也可以貼到 ChatGPT、Gemini 當成 system prompt,本質上是同一塊知識。

⚠️ Copilot vs Agent 視角

原文沒有討論到的：在 GMP-regulated 環境，Skills 的「跨平台可攜」帶來合規風險 — 同一個 .md 在 Claude（已驗證）vs 第三方 AI（未驗證）執行可能產生不同輸出。

建議在你的 SKILL.md frontmatter 加 validated_on: 欄位，明確記錄哪些平台已通過你的內部驗證。

情境 3：專案指令（Project Instructions）

Project Instructions 是 Claude Projects 中的 持久系統提示層（Persistent System Prompt Layer）。

Project Instructions are the persistent system prompt layer inside something like Claude Projects.

差別在於：Skill 管理特定任務，Project Instructions 管理整個脈絡。

Where a Skill governs a specific task, Project Instructions govern an entire context.

最有效的 Project Instructions 應該寫成 Markdown 格式。原文提供了一個基本結構模板（見下方）。

The most effective Project Instructions are written as Markdown files.

作者建議：用這種結構化的 .md，取代直接把 PDF 丟進 AI Project。

Use this instead of injecting a PDF into your AI Projects.

💻 Project Instructions 模板結構

原文提供的六段式架構：Project Name → Context → My role → Always remember → Rules → Format preferences

📚 三層整合的真正威力

Memory（脈絡）+ Skills（任務執行）+ Project Instructions（環境）三者組合時，最大價值是消除大部分的重新解釋與脈絡設定。

你的 Master Prompt v1.5.0（~1053 行）正是這個哲學的高階實踐 — 不過你把三層合併在一個 XML 文件中，並加上 versioning，這比原文建議的「分散在多個 .md」更工程化。

# Project Name

## Context
[這個專案是什麼？目標對象是誰？]

## My role
[我在這個專案中如何使用 Claude？]

## Always remember
[Claude 永遠不該忘記的持久脈絡]

## Rules
[適用於每次對話的具體指令]

## Format preferences
[輸出應該長什麼樣？]

Part V — 如何維護你的 Markdown 系統？

作者直言：建立檔案是簡單的部分，維護才是真正的挑戰。

Building the files is the easy part, but maintaining them is the real challenge.

這呼應了所有知識管理系統共同的失敗模式 — 知識庫腐化（Knowledge Base Decay）。沒有定期清理的個人筆記，6 個月後就會變成「資料墳場」。

原文提供三條維護紀律：

  1. 30 天更新核心 .md — Identity.md、Core Instructions.md 至少每月一次
  2. 60-90 天清理記憶檔 — 用 Cowork 跑 review prompt
  3. 單一工作流，單一檔案 — 不要把所有東西塞到一個 memory.md
⚠️ 60-90 天清理 Prompt

作者提供的清理提示詞（簡譯）：

「請檢視我的 AI Markdown Vault 資料夾。識別並移除過期、已解決、不再相關的條目。整合涵蓋同一主題的條目。保留所有仍然有用的內容。回傳清理後的檔案。」

🛠️ 對照你的「知識 Linting」規格

你正在開發的 Level 1（Python CLI 結構檢查）+ Level 2（LLM 語意判斷）兩級 linting，本質上就是這條維護紀律的自動化、工程化版本。

原文的「每 60-90 天手動跑 prompt」適合個人入門；你已經規劃的方向是對的 — 把它變成自動 cron + tag 完整性 + staleness 偵測。

📚 推薦的資料夾結構

重點整理 Key Takeaways

1. Markdown 是 AI 溝通的最低成本格式
.md 是純文字，沒有 Word/PDF 的隱藏標籤與元資料。在批次自動化、長期累積的情境下，Token 成本與處理速度都優於格式化檔案。
2. 三層架構各司其職
Memory（誰在用 AI）、Skills（執行什麼任務）、Project Instructions（在哪個專案中）— 三者分工清楚才能最大化價值。
3. 維護紀律比建立更重要
30 天更新核心檔、60-90 天清理冗餘、單一工作流單一檔。沒有定期 review，知識庫 6 個月後會變成資料墳場。
4. 跨平台可攜性是真正的鎖定解放
把指令寫成 .md 而非綁在某個 AI 平台的 UI 設定中，當你想換工具或多平台並用時，只需要複製檔案 — 而非重新建立整套設定。

練習題 Practice Questions

先在心中思考答案，再點開展開查看建議答案。

Q1 概念理解 為什麼 Markdown 對 AI 比 Word 或 PDF 更友善？這個論點有什麼潛在的過度簡化？

核心理由（原文觀點）：Markdown 是純文字，沒有隱藏的 XML 標籤、字型定義、邊距設定、二進位資料。AI 必須先過濾這些雜訊才能解析內容，這會消耗 Token 與處理時間。Markdown 幾乎是「輸入即語意」，沒有解析開銷。

潛在過度簡化：

  • 現代 LLM（Claude、GPT-4o）已有強大的多模態解析能力，並非「看不懂」PDF/Word — 只是相對較貴。
  • Word/PDF 在某些情境（含表格、圖表、簽核）仍是業界標準，特別是 GMP 環境。
  • 更精準的說法是「Markdown 訊號雜訊比最高，適合大量自動化」，而非「其他格式失敗」。

這就是 2-3x 折扣原則的應用 — 行銷化的 newsletter 修辭需要降溫到實務價值。

Q2 產業應用 在 GMP 監管的 CDMO 環境中，採用「AI Markdown Vault」三層架構需要做哪些調整？

必須調整的關鍵點：

  • 個人 vs 公司資產分離：Memory.md 中個人偏好可以本地，但任何涉及客戶機密、配方、製程的資訊不能放在個人 Vault — 必須有清楚的資料分級。
  • Skills 需要驗證紀錄：每個 SKILL.md 應該加 frontmatter 紀錄 validated_on:（哪個平台 + 哪個版本驗證過）、review_date:、regulatory_scope:，符合 21 CFR Part 11 的可追溯性要求。
  • 版本控制必要：不能只是「本地 .md 檔案」— 必須上 Git，每次修改有 commit 訊息，能還原到任何歷史版本。
  • Copilot Mode 不是 Agent Mode：原文鼓勵 Cowork 「自動寫檔到資料夾」— 這是 Agent Mode。GMP 環境必須先驗證每次輸出，再人工確認儲存。
  • 定期清理時要有審計軌跡：不能直接刪除舊版 Skill，應該移到 archive/ 並紀錄移除原因與日期。
Q3 批判思考 原文的三層架構（Memory / Skills / Project Instructions）有沒有缺失的層級？你的 Master Prompt 系統補齊了什麼？

原文未明確處理的層級：

  • 輸出格式層（Output Format Layer）：原文 Project Instructions 模板的「Format preferences」太簡略。你的 Master Prompt v1.5.0 用 ~1053 行 XML 定義了完整的設計系統 — CSS 變數、info-box 分類、bilingual layout、code-below 模式。這是把「格式」從一句話升級為可執行規格。
  • Versioning 層：原文沒有講版本管理。你的 v1.5.0 changelog、向後相容承諾、跨欄位 cross-reference（doc-date 必須對齊 doc-file 的日期前綴）— 這是把個人系統變成可信賴基礎設施的關鍵。
  • 後設資料層（Metadata Layer）：原文沒有 dashboard_meta tags。你的 doc-source-type、doc-tags、doc-rating 讓檔案不只是「給 AI 讀」，也是「給 Dashboard 機器索引」。雙重消費者設計。
  • 來源類型分類（Source Type Taxonomy）：v1.5.0 新增的 Anthropic-Docs vs Anthropic-Eng vs 第三方分類 — 這是知識可信度的分層，原文完全沒有對應的概念。

啟示：原文是給「個人初學者」的入門指南，你的系統是「個人運作如同公司」的工程化版本。兩者邏輯同源，成熟度差兩個世代。

原文的「三層架構」（Memory / Skills / Project Instructions）是一個有用的分層心智模型，可以拿來重新檢視我自己的系統 — 我的 Master Prompt v1.5.0 把這三層都壓在一個 XML 文件中，效率高但耦合重；分層思考能幫我識別哪些規則屬於哪一層，未來重構時更容易。
📈 立即應用
本週可做：（1）為現有的 Skills（artifact-skill、cdmo-feasibility、amaran-presentation、開發中的 /triage-deviation）加上 validated_on: 與 last_review: frontmatter，補上 GMP 思維沒有的審計層。（2）把原文的 Project Instructions 六段式模板（Context / Role / Always remember / Rules / Format）借來當作我的 Skill graph 探索的基礎節點結構。
⚠ 需要補充
原文嚴重缺失：（1）GMP / 合規視角完全沒有 — 採用前必須加上資料分級、審計軌跡、版本控制設計。（2）多人協作場景沒有討論 — 原文純粹是個人 PKM，但實務上 Skills 通常需要團隊共享、誰負責維護的治理問題。（3）原文的「移除過期條目」過於簡化 — 對知識管理而言，archive 比 delete 更合適，原文沒有區分。三個月後重讀時，重點應該放在「我的系統相對於這個入門框架已經進化到哪裡」而非學新東西。
